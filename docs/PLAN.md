# 찬양 인도자용 반주 생성 앱 — 개발 계획

## Context

찬양 인도자가 그날 부를 곡 4~5개의 코드 악보(가사+코드, 오선 없음)를 사진으로 업로드하면, 앱이 피아노/기타/베이스/드럼 등 주요 악기 음원을 자동 생성해 반주 트랙을 만들어주고, 예배 중 실시간으로 "1절로 돌아가기", "후렴 반복", "다음 곡" 같은 선택을 하면 끊김 없이 이어서 재생되는 서비스를 만드는 것이 목표입니다.

현재 `/Users/chelly/workspace/praise`는 빈 디렉토리이며, 완전히 새로 시작하는 프로젝트입니다. 사용자는 빠른 완성보다 **완성도**를 우선시하며, 여러 교회가 실제로 쓸 수 있는 제품 수준의 서비스를 목표로 하고 있습니다. 확인된 전제:
- 악보 형태: **오선보 위에 멜로디 음표 + 코드 기호 + 가사가 함께 표기된 정식 리드시트** (실제 샘플 확인 완료 — 순수 "코드+가사만" 형태가 아니라, 음표머리·박자·이음줄·도돌이표까지 포함된 리드시트임). 단, **멜로디 음정(pitch) 자체는 재생 목적상 불필요**하다고 확인 — 코드/가사/마디·박자 구조만 정확하면 반주 생성에 충분. 곡 구조 라벨(절/후렴 등)은 악보에 명시되지 않으므로 **자동 추론 우선, 인도자는 예외만 수정**하는 방식으로 처리.
- 플랫폼: **웹 앱 우선**, 이후 네이티브 앱(iOS/Android)으로 확장
- 음원 생성 방식: **MIDI + 샘플/신디사이저 기반** (생성형 오디오 모델이 아님)
- 목표 범위: **여러 교회가 쓸 수 있는 SaaS 제품** (멀티테넌시, 인증, 결제까지 고려)

이 문서는 각 레이어별 기술 선택과 7단계 로드맵을 정리한 것입니다. 조사와 설계는 Plan 서브에이전트를 통해 검증했고, 실제 악보 샘플 확인 후 OCR 파이프라인 섹션을 보완했습니다.

### 핵심 데이터 모델

`Song → Section(절/후렴/브릿지 등, order_index) → Line(가사) → ChordEvent(코드, 문자 오프셋+박자 오프셋)`, 별도로 `Arrangement → InstrumentTrack(악기별 MIDI)`. 모든 타이밍은 **박자(beat) 단위**로 저장하고 재생 시점에만 초 단위로 환산 — 템포 변경, 구간 점프, 반복 로직이 전부 이 위에서 동작합니다. Section은 단순 리스트가 아니라 "1절→2절→후렴→브릿지→후렴→아웃트로"라는 기본 순서를 가지되, 실시간 점프는 이 그래프의 임의 노드로 이동하는 구조입니다.

### OCR 파이프라인 (실제 악보 샘플 반영, 수정됨)

**실제 샘플 확인 결과, 이 악보는 오선보+음표+코드+가사가 모두 있는 정식 리드시트입니다.** 순수 코드 차트보다 시각적으로 복잡하지만, 멜로디 음정 자체는 재생에 불필요하다고 확인했으므로 **완전한 OMR(음정까지 정밀 인식)은 하지 않고, "마디/박자 구조 + 코드 + 가사 + 도돌이표/구조 마커"만 추출하는 축소된 파이프라인**을 채택합니다. 이는 여전히 광학 음악 기호를 다뤄야 한다는 점에서 순수 텍스트 OCR보다는 어렵지만, 정밀 음정 OMR(예: Audiveris 급 엔진 도입)보다는 훨씬 가볍습니다.

- **1차 추출 — 비전 LLM(Claude vision) 직접 호출**: 이미지를 페이지별로 잘라 비전 LLM에 전달, 엄격한 JSON 스키마로 다음을 요청합니다 — (1) 가사 텍스트(한글, 음절 단위), (2) 코드 기호와 그 코드가 걸리는 가사 내 문자 오프셋, (3) 마디(바라인) 경계와 각 줄의 박자 수(정확한 음가까지는 아니어도, 몇 박자짜리 줄인지, 도돌이표가 있는지 정도는 비전 LLM이 오선보의 마디선/음표 그룹핑을 보고 추정), (4) 조표(Key)와 박자표. 오선보가 있다는 것이 오히려 코드의 정확한 박자 위치를 추정하는 데 도움이 됩니다(음표머리 위치 = 박자 위치).
- **정확도 유의사항(검증 결과 반영)**: Claude Vision 공식 문서는 "spatial reasoning"과 "counting, especially with large numbers of small objects"를 명시적 한계로 언급합니다. 가사·코드·조표(텍스트 판독)는 신뢰도가 높은 편이나, 마디 경계·줄당 박자 수(작은 기호를 세고 위치를 추정하는 작업)는 이 한계에 정확히 해당하므로 정확도를 사전 보장할 수 없고 Phase 1 실측이 필요합니다. 완화책으로 (1) 텍스트 추출과 마디/박자 구조 추출을 별도 호출로 분리, (2) `output_config.format`(Structured Outputs)으로 JSON 스키마를 강제해 형식 오류를 제거, (3) 필요 시 2회 호출 후 불일치 시 자동으로 `needs_review` 플래그를 다는 self-consistency 체크를 적용합니다.
- **2차 검증 — 코드 문법 검증기(결정론적, 비-LLM)**: 추출된 코드 문자열을 정규식 문법(`^[A-G](#|b)?(maj7|m7|m|7|sus2|sus4|dim7?|aug|add9|6|9|...)?(/[A-G](#|b)?)?$`)으로 재검증, 실패 시 `needs_review` 플래그. Dsus⁴, C⁶처럼 위첨자로 표기된 코드도 이 문법에 포함해 처리.
- **섹션(절/후렴 등) 자동 추론**: 악보에 구조 라벨이 없으므로, 추출된 가사 줄들 간의 반복 패턴(같은 코드 진행+비슷한 리듬이 반복되는 줄 묶음)과 도돌이표 위치를 근거로 LLM이 절/후렴/간주(예: "라라라" 같은 보칼리제이션 구간) 등을 best-guess로 라벨링합니다. 정확도가 100%일 필요는 없음 — **인도자가 교정 UI에서 라벨을 클릭 한 번으로 바꿀 수 있게 하는 것**이 핵심 방어선입니다.
- **필수 수동 교정 UI**: 원본 이미지와 나란히 편집 가능한 화면 제공 — 코드 위치 드래그 이동, 가사 수정, 섹션 라벨 재지정(1절/후렴/브릿지/간주 등 드롭다운), 키/템포/박자 확정. OCR/LLM 결과를 100% 신뢰하지 않고 이 단계를 정확도의 최종 방어선으로 설계합니다.
- 4~5장의 이미지는 이미지별로 추출 후 별도의 병합/정렬 단계를 거칩니다.

**대안(장기 검토용)**: 만약 나중에 멜로디 참고 트랙 재생이 필요해지면(예: 신규 인도자를 위한 멜로디 가이드), Audiveris 같은 정식 OMR 엔진을 별도 파이프라인으로 추가하는 것을 고려할 수 있으나, 이는 MVP 범위 밖입니다.

### 편곡(MIDI 생성) 엔진

ML 기반 생성(예: Magenta류)이 아니라 **규칙/템플릿 기반 편곡**을 채택합니다 — 장르별 반주 패턴 라이브러리(예: `praise_upbeat`, `ccm_ballad`, `hymn_traditional`, `acoustic_intimate` 등 3~4개 프리셋)를 악기별(피아노 컴핑, 기타 스트로크/핑거피킹, 베이스 루트-5도, 드럼 그루브)로 구축하고, 코드 기호→음정 해석에는 **Tonal.js**를 사용합니다(`Voicing`/`Voice-Leading` 모듈이 코드 간 성부 연결도 제공해 별도 구현 없이 활용 가능). 섹션별로 악기 밀도/다이나믹스를 다르게 하는 것만으로도(예: 1절은 피아노만, 후렴은 풀밴드) 체감 품질이 크게 올라갑니다.

### 실시간 구간 점프 재생 엔진 (기존 계획보다 난이도 하향 — 검증 결과 반영)

**직접 구현이 아니라 `smplr` v1.0.0의 내장 시퀀서를 사용합니다.** 소스 코드 확인 결과 `smplr`은 lookahead 스케줄러, tick 기반 `TransportClock`, 라이브 `seek`, `bpm` 변경, 패턴 체이닝을 이미 제공하므로 "Tale of Two Clocks" 스케줄러를 처음부터 만들 필요가 없습니다. 모든 타이밍은 tick(박자) 단위로 다루고 재생 시점에만 `tickToAudioTime()`으로 초 환산되어, 이 문서가 원래 전제한 "박자 단위 저장, 재생 시 환산" 원칙을 라이브러리 레벨에서 그대로 충족합니다.

다만 확인된 두 가지 갭은 앱에서 직접 메워야 합니다:
1. **마디 경계 정렬**: `smplr`의 `position` setter(`seek`)는 즉시형이라, 버튼을 누르면 그 즉시 점프합니다. "현재 마디가 끝나는 시점까지 기다렸다가 이동"하는 로직은 앱이 다음 마디 경계 tick을 계산해 그 시점까지 점프를 지연시키는 얇은 래퍼로 구현해야 합니다.
2. **예약된 노트 잔향**: 점프 직전 lookahead 창(약 100~150ms) 안에 이미 예약된 이전 구간 노트는 `position` 변경만으로는 취소되지 않습니다. 위 1번(마디 경계 정렬)을 구현하면 대부분 자연스럽게 묻혀 무해해집니다.

각 곡은 `현재 섹션 → 가능한 전환(다음 섹션/반복/특정 섹션 점프/다음 곡)` 상태 머신으로 모델링하고, UI는 이 상태의 `transitions`를 그대로 렌더링합니다. "마지막 소절 반복"은 섹션보다 세밀한 단위(Line)로 점프하는 동일한 메커니즘입니다.

**의존성 리스크**: `smplr`은 GitHub 스타 수 기준 소규모 프로젝트로 사실상 단일 메인테이너가 관리합니다. 버전을 v1.0.0으로 고정하고, 시퀀서 API를 얇은 자체 어댑터 레이어로 감싸 향후 교체 가능성을 확보하는 것을 권장합니다.

**재생 안정성**: Web Audio는 사용자 제스처로 `AudioContext`를 활성화해야 하며, iOS Safari는 화면 잠금·백그라운드 전환 시 컨텍스트를 suspend합니다. 예배 중 반주가 끊기는 것은 치명적이므로, Wake Lock API로 화면 꺼짐을 방지하고 `AudioContext` suspend를 감지해 자동으로 resume하는 처리를 재생 엔진에 포함합니다.

## 단계별 로드맵

**Phase 0 — 기반 인프라 (2~3주)**
Next.js 스캐폴딩, WorkOS/Clerk 인증(Organization=교회), Postgres 마이그레이션 도구(Prisma/Drizzle)로 핵심 스키마 스텁 생성, R2 업로드 엔드포인트, Inngest 연결, CI, Sentry.
완료 기준: 로그인한 사용자가 이미지를 업로드하면 R2+DB에 저장되고 실제 URL로 배포되어 동작.

**Phase 1 — 악보 업로드 + OCR + 수동 교정 UI (5~7주, 실제 악보 형태 반영으로 기존 계획보다 1주 증가)**
멀티 이미지 업로드, 비전 LLM 추출 잡(가사/코드/조표 추출과 마디/박자/반복 구조 추출을 별도 호출로 분리) + `output_config.format`(Structured Outputs)으로 JSON 스키마 강제 + 코드 문법 검증, 나란히 보는 교정 UI(코드 드래그 이동, 가사 수정, 섹션 재배열/재라벨, 키/템포/박자 설정). 이 단계에서 비전 LLM 모델 등급(Sonnet vs Haiku)을 실제 악보로 비교 테스트해 비용/정확도 균형점을 확정하고, **마디/박자 구조 추출 정확도를 별도로 실측**(공식 문서가 이 유형의 작업을 spatial reasoning/counting 한계로 명시하므로 가사·코드 추출과 신뢰도가 다를 수 있음). 실시간 구간 점프 최소 스파이크(한 곡·한 장르·섹션 2개, `smplr` 시퀀서 기반)도 이 단계와 병행.
완료 기준: 실제 한국 교회 리드시트(오선+코드+가사) 10장 이상을 업로드→추출→각 5분 이내 교정→저장까지 성공, 섹션 자동 추론이 대부분의 경우 큰 수정 없이 사용 가능, 마디/박자 구조 추출 정확도가 실사용 가능한 수준인지 확인.

**Phase 2 — 데이터 모델 확정 + 단일 악기 반주 (4~5주로 상향, Setlist 스키마 반영)**
박자 기반 타이밍 계산 확정(Section/Line의 start_beat·length_beats, ChordEvent.beat_offset 기준 확정), **Setlist/SetlistItem 스키마 확정(order_index, arrangement_id 참조 — Phase 5 멀티테넌시 작업 전 기본 모델을 여기서 먼저 고정)**, Tonal.js 코드 보이싱 엔진, 단일 악기(피아노, 블록코드) 편곡 생성기(구조화된 노트 이벤트 JSON으로 저장 — `smplr` Sequencer에 직접 투입 가능한 형식), 필요 시 노트 이벤트 → MIDI 파일 변환은 별도 내보내기 기능으로 부가, `smplr` 재생(재생/일시정지/탐색만, 점프 로직 없음).
완료 기준: 저장된 곡이 정확한 타이밍에 코드 변화가 들리는 피아노 반주로 재생됨. Setlist/SetlistItem에 여러 곡을 순서대로 저장·조회할 수 있음(UI 없이 API/DB 레벨 검증으로 충분).

**Phase 3 — 다악기 편곡 + 세트리스트 구성 UI + 샘플 재생 품질 (6~8주로 상향, 세트리스트 UI 반영)**
기타/베이스/드럼/패드 패턴 라이브러리(3~4개 장르 프리셋), 섹션별 다이나믹스/악기 구성 맵, 사운드폰트 선정/튜닝, 악기별 볼륨 믹싱. **더불어 세트리스트 구성 페이지 UI(F011): 저장된 곡 검색·추가, 드래그 순서 정렬, 곡 제거, "예배 시작" 버튼** — Phase 2에서 확정한 Setlist 모델 위에 구현하며, Phase 4의 "다음 곡 전환" 기능이 이 UI가 만든 순서 데이터를 그대로 소비하도록 준비합니다.
완료 기준: 실제 인도자가 블라인드로 듣고 "리허설에 쓸 만하다"고 평가. 세트리스트에 곡 3곡 이상을 추가·재정렬·저장하는 흐름이 실제로 동작.

**Phase 4 — 실시간 구간 점프 재생 엔진 (3~4주로 하향, 검증 결과 반영)**
`smplr` 내장 시퀀서 위에 마디 경계 정렬 점프 래퍼 구현(위 "실시간 구간 점프 재생 엔진" 절 참조) + 자동화된 타이밍 테스트, 섹션 전환 상태 머신, 실시간 "다음 선택지" UI, 반복/점프/**다음곡(Phase 3에서 구현한 Setlist 순서를 따라 전환)** 기능 전부 무결점 동작, 재생 안정성(Wake Lock, AudioContext 자동 재개), PWA 오프라인 캐싱(사운드폰트+반주 데이터 사전 다운로드).
완료 기준: 데스크톱 크롬과 모바일 사파리 양쪽에서 실제 예배 시뮬레이션(세트리스트 다곡 전환 포함) 시 오디오 끊김 없음.
→ **리스크 완화 (Phase 1로 이동)**: `smplr` 시퀀서 발견으로 점프 기능의 최소 버전 스파이크(한 곡·한 장르·섹션 2개)가 며칠 규모로 가능해졌으므로, Phase 4까지 기다리지 않고 **Phase 1과 병행해 조기 검증**합니다.

**Phase 5 — 멀티테넌시/결제 프로덕션화 (4~5주)**
Postgres RLS로 조직 간 데이터 격리(**Setlist/SetlistItem을 포함해 Phase 2~3에서 만든 모든 테이블에 조직 스코프 적용**), 조직 내 역할(관리자/인도자/멤버), 토스페이먼츠 구독 연동, 사용량/쿼터 추적, 모니터링/백업.
완료 기준: 두 번째 교회가 가입→결제→사용까지 하되 데이터 유출이 전혀 없음(세트리스트를 포함한 격리 테스트로 검증).

**Phase 6 — 네이티브 모바일 앱 (React Native/Expo) (6~10주)**
공유 타입/API 재사용, 네이티브 오디오 엔진 스파이크(Web Audio 폴리필이 아닌 별도 리서치 필요), 오프라인 우선 동기화.
완료 기준: 핵심 실시간 재생 플로우가 PWA와 기능 동등, TestFlight/Play 내부 테스트에 실제 교회 배포.

## 우선 생성할 핵심 파일

1. `prisma/schema.prisma` (또는 `drizzle/schema.ts`) — Song/Section/Line/ChordEvent/Arrangement/InstrumentTrack 스키마. 다른 모든 레이어가 여기 의존하므로 가장 먼저 확정.
2. `src/lib/song-model/types.ts` — 교정 UI와 편곡 엔진이 공유하는 곡 데이터 타입.
3. `src/jobs/extract-chart.ts` — 비전 LLM 호출 + 코드 문법 검증 Inngest 잡.
4. `src/lib/arrangement/generate.ts` — 규칙 기반 편곡 엔진 (제품의 핵심 IP).
5. `src/lib/playback/scheduler.ts` — Web Audio lookahead 스케줄러 + 섹션 점프 상태 머신 (가장 테스트가 중요한 모듈).

## 검증 방법

- Phase 1 완료 후: 실제 코드 악보 사진 10장 이상으로 업로드→추출→교정 워크플로우를 직접 실행해보고 정확도/소요시간 측정.
- Phase 2~3: 생성된 MIDI를 실제로 재생해 코드 진행과 리듬이 자연스러운지 청취 테스트, 가능하면 실제 인도자 대상 블라인드 테스트.
- Phase 4: 자동화 테스트(스케줄러의 경계 타이밍 유닛 테스트)로 이벤트 누락/중복이 없는지 검증 + 데스크톱 크롬·모바일 사파리에서 실제 예배 시나리오 리허설.
- Phase 5: 두 개 이상의 테스트 조직 계정으로 데이터 격리 여부를 직접 확인하는 멀티테넌시 격리 테스트 작성.
